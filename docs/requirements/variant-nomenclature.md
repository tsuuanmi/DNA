# Variant Nomenclature Requirements

**Requirement namespace:** `SRS-NOM-*`

These requirements are part of the canonical [[requirements/SRS|DNA SRS]].

- **SRS-NOM-001:** Target-specific variant nomenclature MUST be an optional post-calling representation capability. It MUST NOT reinterpret sequencing signal, change caller eligibility, manufacture phase, or change the represented biological haplotype.
- **SRS-NOM-002:** A nomenclature operation consuming a normalization result MUST verify that the supplied reference name and sequence identity match the reference identity carried by that result.
- **SRS-NOM-003:** The represented variant set MUST reconstruct exactly the same complete alternate sequence as the normalized variant set. Source variants, normalized variants, reference identity, and the reconstructed alternate sequence MUST remain available in the result.
- **SRS-NOM-004:** Nomenclature windows, their reference sequences, structures, and ordered rules MUST come from the target profile (SRS-PRF-006). Rule preconditions: `anchored_run_lengths` needs a window of repeat bases around exactly one anchor; `anchored_tract` needs a window led by a run of another base, then repeat bases around exactly one anchor with a repeat base on each side; `anchor_duplication` and `anchor_deletion` need a repeat base after the anchor; the anchor rules and `terminal_repeat_insertion` need an `anchored_homopolymer` structure; `motif_shift` needs a `tandem_repeat` window ending with its motif. A reference that does not carry every profile window sequence at its position MUST fail explicitly (SRS-PRF-005). SRS-NOM-005, -006, and -013 to -015 specify the shipped human-mtDNA profile (`config/profiles/human-mtdna-rcrs.toml`): HVS-II 303-315 `CCCCCCCTCCCCC` (`T` anchor at 310), HVS-III 512-524 `AGCACACACACAC`, and HVS-I 16180-16193 `AAAACCCCCTCCCC` (`T` anchor at 16189).
- **SRS-NOM-005:** When the HVS-II alternate window contains only `C` and `T` bases with a `T`, the first `T` MUST split the window: a change in the length of the `C` run before it MUST be represented at the 309 boundary (`309.1C`, `309DEL`), and the rest MUST be represented left-anchored against 311-315 as position-wise substitutions plus `C` insertions after 315 or deletions from 315 backwards (`315.1C`, `312T 315.1C 315.2C 315.3C`, `315DEL`).
- **SRS-NOM-006:** Multiple inserted C bases at the left HVS-II run MUST remain anchored after position 309 and multiple inserted C bases at the right run MUST remain anchored after position 315 so an outer notation layer can render ordered forms such as `309.1C`, `309.2C`, and `315.1C`.
- **SRS-NOM-007:** Variants outside every nomenclature window MUST be preserved unchanged. When an edit crosses a validated window boundary, that window's edits MUST keep their normalized representation and none of them MUST be rewritten; every other window MUST still be represented.
- **SRS-NOM-008:** Within a window, the first rule whose candidate reconstructs exactly the same window haplotype MUST be used; when no rule applies, the normalized representation MUST be preserved rather than another decomposition invented.
- **SRS-NOM-009:** Nomenclature MUST NOT implement Sanger repeat-artifact interpretation, primer callable ranges, decimal notation rendering, sample reconciliation, or NGS-specific behavior.
- **SRS-NOM-010:** When the target profile declares `notation`, the `sample`, `call`, and `notation` workflows MUST represent each read's eligible variants independently: the profile normalization followed by the profile nomenclature windows. A window that an edit of the read crosses MUST keep its normalized representation; the read's other windows MUST still be represented. A window MUST keep its normalized representation when its representation would place a call where the read reads nothing (a substituted or deleted base, or an insertion's anchor base, outside the read's callable reference segments), or when a base the rule's choice of form rests on lies outside them (design: variant nomenclature). When the profile declares no notation the workflow MUST NOT produce notation.
- **SRS-NOM-011:** The `per_base_decimal` notation style MUST render represented variants one call per changed base: a substitution as `<position><base>`, each deleted base as `<position>DEL`, and each inserted base as `<anchor>.<ordinal><base>` after the preceding reference base (anchor `0` before position 1), ordered by position and then ordinal.
- **SRS-NOM-012:** Sample notation MUST list each distinct rendered call with every read whose represented variants contain it, in read-registry order. It MUST NOT include ineligible observations, infer reference support from a read's silence, or adjudicate disagreement between reads.
- **SRS-NOM-013:** After the run-length rule (SRS-NOM-005), HVS-II MUST represent a duplicated anchor as `311T 315.1C`, an anchor deletion as `310C 315DEL`, and a one-base gain ending in `C` as position-wise substitutions plus `315.1C` (EMPOP terminal insertion), the last only when that needs no more edits than the normalized form. A substitution without length gain MUST NOT gain `315.1C`.
- **SRS-NOM-014:** HVS-III (512-524) MUST represent the loss or gain of whole `AC` motif copies at the window's 3' end (`523DEL 524DEL`, `524.1A 524.2C`) plus position-wise substitutions against the remaining reference (`513A 523DEL 524DEL`), and an unchanged window length as position-wise substitutions.
- **SRS-NOM-015:** HVS-I (16180-16193) MUST represent the haplotype of `16183C 16184A 16189C` in that phylogenetic form whatever its source decomposition. Otherwise, while `T16189` sits before a second `C` run of four bases, a shorter A-tract MUST be deletions ending at 16183, the first `C` run MUST be written left-anchored from 16184 with `C` insertions after 16188 or deletions ending at 16188, and the second run as substitutions; any other window MUST be written left-anchored from 16180 as substitutions plus `C` insertions after 16193 or deletions ending at 16193 (`16182C 16183C 16189C`, `16189C 16190T 16193.1C 16193.2C`, `16189C 16193DEL`).
- **SRS-NOM-016:** When the profile declares conformance, `notation` MUST check each read's represented variants against the declared rules (`insertion_at_run_end`, `insertion_matches_run`) over reference homopolymers of at least `minimum_run_length` bases and MUST report every finding without changing any represented call or the reconstructed haplotype.
- **SRS-NOM-017:** A profile report convention (`[[nomenclature.conventions]]`) MUST label every rendered call it covers in each notation view (`sample`, `call`, `notation`, and `SampleAnalysis::call`), and MUST NOT drop, add, or rewrite a call or change the reconstructed haplotype. It MUST match only on a read's represented calls and the reference, never on read evidence. `run_length` covers an inserted `base` whose anchor lies in `window`, and a deleted `base` in `window`, when the read's represented haplotype has an uninterrupted run of `base` of at least `minimum_run` bases at the call, counting a deleted base in the run it shortens; it never covers a substitution. A distinct call is labelled only when every read containing it labels it with the same convention.
- **SRS-NOM-018:** When the profile declares `[empop]`, `notation` MUST export an offline EMPOP query and send it nowhere. Its interpretation ranges MUST cover exactly the profile-region positions that one record of the variants document calls (its callable reference segments, SRS-VAR-019), in the profile's region order and then position order, merged where they touch; a record position no range covers MUST be listed with its reason (`unresolved`, `excluded_variant`, `not_analysed` for a position the call does not analyse (SRS-CONS-012), `overlap`). The mitotype MUST hold the represented calls inside the ranges, distinct and ordered by position and insertion ordinal, an insertion written when its anchor lies in a range (EMPOP numbers `X.k` at `X`), labelled calls included, and IUPAC codes passed through. `SampleAnalysis::call` MUST give the same query.
