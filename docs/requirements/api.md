# Public API Requirements

**Requirement namespace:** `SRS-API-*`

These requirements are part of the canonical [[requirements/SRS|DNA SRS]].

- **SRS-API-001:** DNA MUST expose a Rust library capability for reference-guided Sanger Variant Analysis without requiring callers to construct CLI/`clap` types.
- **SRS-API-002:** The Sanger Variant Analysis API MUST accept explicit AB1, reference FASTA, and configuration paths and MUST reuse the same scientific read-processing, alignment, and variant-calling behavior as the production CLI.
- **SRS-API-003:** The Sanger Variant Analysis API MUST return typed result data containing input/configuration identities, reference identity, covered reference segments, and evidence-backed reportable variants. The public result MUST NOT expose the versioned JSON report DTO as its domain contract.
- **SRS-API-004:** Calling the Variant Analysis API MUST NOT create operational log files, derive or validate CLI output paths, serialize JSON, or publish result files.
- **SRS-API-005:** Public reference segments MUST use explicit zero-based half-open coordinates and public variant positions MUST use explicit one-based coordinates.

- **SRS-API-006:** `VariantAnalysisResult` MUST expose a typed `CalledVariantSet` projection that carries one reference identity plus the reportable called variants without implying a right/left alignment, nomenclature, or interchange-format normalization policy.
- **SRS-API-007:** DNA MUST expose optional post-calling variant normalization as a separate Rust capability accepting an explicit normalization policy; using Variant Analysis MUST NOT implicitly invoke that capability.
- **SRS-API-008:** DNA MUST expose target nomenclature as a separate optional capability boundary that applies the windows of an explicitly supplied target profile (`variant_nomenclature::apply`) and MUST NOT silently apply any target's nomenclature rules.
- **SRS-API-009:** DNA MUST expose a Rust library capability for Sanger sample analysis (`sample_analysis::analyze_sanger`) that accepts explicit trace, reference FASTA, and configuration paths and an explicit maximum number of worker threads, processes and places each trace once, and returns both the sample evidence and the consensus from that one placement pass. It MUST reuse the same read-processing, placement, rejection, aggregation, and consensus behavior as the `sample` and `consensus` commands. A companion call (`sample_analysis::analyze_sanger_outcome`) MUST run the same pass and return, when no read is admitted, every rejected read with its cause instead of the `NoAdmittedReads` error, and otherwise exactly the same analysis or error.
- **SRS-API-010:** The Sample Analysis result MUST be typed: reference and target-profile identities, the target profile's reportable regions, the core sample evidence (which carries the configuration identity), the consensus, the Sanger evidence of each admitted read, and each rejected read with its cause and, unless it was too short to process, its Sanger evidence, keyed by read content SHA-256. It MUST NOT expose the versioned JSON report DTOs.
- **SRS-API-011:** Calling the Sample Analysis API, including `SampleAnalysis::call`, MUST NOT create operational log files, derive or validate CLI output paths, serialize JSON, or publish result files. Its result MUST NOT depend on the number of workers or on how its reads are scheduled, and a failure MUST be that of the first failing trace in input order, whether a typed error or a panic. Each read's instrumentation MUST go to the caller's current dispatcher inside the caller's current span.
- **SRS-API-012:** A Sample Analysis MUST be callable in process (`SampleAnalysis::call`) for a given sample identifier: the consensus MUST be called with the analysis's configuration, profile, and reference exactly as `call` calls the consensus document that `consensus` publishes, from the consensus's decided edits (SRS-VAR-021), completing the recommended `consensus` then `call` workflow. The typed result MUST hold the consensus segments' callable reference segments and the sample's notation calls exactly as `notation.calls[].call` of the `dna.variants/v1` document `call` would publish, each with its position, insertion ordinal, and reference and called bases.
- **SRS-API-013:** A Sample Analysis MUST expose, read-only (`SampleAnalysis::observations`), every admitted read's observation of each reference position of a requested inclusive 1-based interval that a read covers, whether or not a read differs from the reference there, as the same observation records and with the same read indices as the differential loci of the sample evidence, without their support aggregates. A zero or reversed interval MUST fail typed; the interval does not wrap the circular origin. It MUST NOT change the sample evidence or the consensus.
- **SRS-API-014:** `dna review <sample-id> <trace>... --reference <fasta> [--signal <file>]` MUST run the in-process path of SRS-API-012 once (the sample placement pass with its rejections, the consensus, and `SampleAnalysis::call`) and write one `results/<sample-id>.review.json` identified as `dna.review/v1`, failing without output only on an input, configuration, or publication error. Every sample MUST get a document whose `status` is `called`, `rejected` (every read rejected; the reads with their causes and no items), or `call_failed` (the failure text, and the items without calls). The document MUST carry the provenance with the labelling-rules version, every read with its strand, the stretches of reportable positions its signal leaves masked (from the read's own callability, never fixed positions), and its phase mixtures with each component compared with the reference on its own (ADR-0082, display only), or its rejection, the sample's calls, callable ranges, EMPOP query, and the zones that tile the reportable regions (bounded only by the profile's repeat windows and the sample's own reads, each with the `check` items touching it), and the reportable positions the consensus decided by reference confirmations alone (ADR-0080) when the call succeeded, the review items in priority order with their labels and per-read evidence, and a summary whose `clear` holds only for a called sample without a `check` item. Items and labels MUST follow the rules of the [review reference](../reference/review.md), derive from DNA's own evidence only, and be byte-identical for the same inputs whatever the number of workers. With `--signal`, the command MUST read the `dna.signal/v1` file (SRS-CALL-019), validated as SRS-API-016 writes it, take the sample's own admitted reads out of it, judge second-channel thresholds against it (SRS-CALL-020), and record its run identifier, SHA-256, and selection version in provenance; a run signal that holds none of the sample's admitted traces MUST fail the command without output.
- **SRS-API-015:** A Sample Analysis whose consensus was called MUST expose, in process (`SampleAnalysis::review_checks`), the items of its review list that a reviewer must look at (`check` items of SRS-API-014), each with its first and last reference positions (1-based) and its label names, built by the same rules as `dna review` with an optional in-process run signal in place of `--signal`, with no file, log, or document written.
- **SRS-API-016:** `dna signal <run-id> <trace>...` MUST write one deterministic `results/<run-id>.signal.json` identified as `dna.signal/v1` (SRS-CALL-019) with the configuration's SHA-256 and the plugins in its provenance, whatever the order of the traces: reads the sample commands reject are counted but contribute nothing, and an unreadable input, an invalid configuration or run identifier, or an existing target fails the command without output.
- **SRS-API-017:** `dna evidence <trace>` MUST write one deterministic `results/<trace-stem>.evidence.json` identified as `dna.read_evidence/v1`, without a reference, naming the trace's file name and SHA-256 in provenance: the read's `ReadEvidence` exactly as the core receives it from the Sanger plugin (every call's base, profile weights, placement, per-use verdicts with their reasons verbatim, run bound, second base, `second_unexplained`, and `reference_only`; the informative interval, reason order, ends, and phase mixtures) with the Sanger signal each rests on (locus scan, the selected A/C/G/T peak of each channel in its window, primary-event A/C/G/T heights, relative quality, second-peak cause), and the Sanger evidence the analysis and sample documents report (trim, callability, signal quality, and warning counts), every number at full precision, its bases, trim, callability, signal quality, and warnings equal to `dna basecall`'s for the same trace and configuration. A read the sample commands set aside before the core (SRS-SAMPLE-027, SRS-SAMPLE-030) MUST instead get a document with its rejection as the sample documents report it (the measured count and its configured minimum) and, for a read with too few callable calls, its integrity and callability. An unreadable input, an invalid configuration, another failure of the Sanger plugin, or an existing target fails the command without output (PROP-0011).
- **SRS-API-018:** `dna analyze --evidence <document> --reference <fasta>` MUST place and call a read from its `dna.read_evidence/v1` document alone, without the trace, and write the analysis document byte-identical to the one `dna analyze <trace> --reference <fasta>` writes for the trace the document was written from under the same configuration (SRS-IN-010 names it). The document MUST be at most 16 MiB, closed in shape, written under the loaded configuration (its SHA-256) by this build's evidence plugins, with its calls in call order, every reason label one the Sanger plugin raises, and its trim, callability, noisy regions, and warnings consistent with its calls; its evidence MUST be rebuilt through the kernel's own constructors. The document of a read set aside MUST fail the command with the error the analysis of its trace fails with. Any other document fails the command with a typed error and without output (PROP-0011).
- **SRS-API-019:** `dna sample`, `dna consensus`, and `dna review` MUST accept `--evidence <document>...` in place of the sample's traces, never both: one `dna.read_evidence/v1` document per read, read as SRS-API-018 reads it (a set-aside read's document included, its recorded rejection checked against the loaded configuration's minimum). Each MUST place every read from its document as the trace-based command places the read of its trace, reject a set-aside read with its recorded cause and evidence, name every read by the stem of the trace file name its document records, and write its documents byte-identical to those the trace-based command writes for the traces the documents were written from under the same configuration, `dna review --signal` included (PROP-0011).
- **SRS-API-020:** The review MUST judge the runs of each profile window whose rules split two runs of one base by an anchor base (`anchored_homopolymer`) from the admitted reads' tract decodes (SRS-CALL-025, [[PROP-0012]] increment 3), and MUST decide nothing.
  - **Credit.** A decode MUST be credited to the run its first call is aligned to, or, on an inserted column, the nearest aligned call before it in the read's order, when its run base is the window's repeat base on the read's strand.
  - **Lengths.** A read MUST give the length of the run it enters first from its first-run marginal. When it chose the window's anchor as its mark and both its marginals are clear, it MUST also give the next run's length, its total less the first and the mark. A read whose consensus reading shows a run in phase, its calls clean and counted and both ends shown by unmasked calls of another base (ADR-0074, `dna_consensus::read_runs_over`), MUST give that run's length too.
  - **Strands.** A strand MUST give a run one clear length only when every length its reads give is clear and equal.
  - **Confirmation.** A run MUST be confirmed only when its reads give it DNA's decided length: both strands give it one clear length, the same, or one strand gives none and the other gives one clear length that at least one of its reads shows in phase. A run whose views on one strand are decodes alone MUST NOT be confirmed by that strand without the other. A read structure other than DNA's (a mark where DNA calls one run, or none where it calls two) MUST never confirm.
  - **Labels.** In a window whose run lengths the profile records, every run that a decode reaches and that is not confirmed MUST be labelled `length_unconfirmed`, a check. In a window over which a `run_length` convention leaves its repeat base's runs unrecorded, every run a decode reaches MUST be labelled `length_not_recorded`, context and never a check. A window no decode reaches MUST get no label.
