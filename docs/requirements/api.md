# Public API Requirements

**Requirement namespace:** `SRS-API-*`

These requirements are part of the canonical [DNA SRS](SRS.md).

- **SRS-API-001:** DNA MUST expose a Rust library capability for reference-guided Sanger Variant Analysis without requiring callers to construct CLI/`clap` types.
- **SRS-API-002:** The Sanger Variant Analysis API MUST accept explicit AB1, reference FASTA, and configuration paths and MUST reuse the same scientific read-processing, alignment, and variant-calling behavior as the production CLI.
- **SRS-API-003:** The Sanger Variant Analysis API MUST return typed result data containing input/configuration identities, reference identity, covered reference segments, and evidence-backed reportable variants. The public result MUST NOT expose the versioned JSON report DTO as its domain contract.
- **SRS-API-004:** Calling the Variant Analysis API MUST NOT create operational log files, derive or validate CLI output paths, serialize JSON, or publish result files.
- **SRS-API-005:** Public reference segments MUST use explicit zero-based half-open coordinates and public variant positions MUST use explicit one-based coordinates.

- **SRS-API-006:** `VariantAnalysisResult` MUST expose a typed `CalledVariantSet` projection that carries one reference identity plus the reportable called variants without implying a right/left alignment, nomenclature, or interchange-format normalization policy.
- **SRS-API-007:** DNA MUST expose optional post-calling variant normalization as a separate Rust capability accepting an explicit normalization policy; using Variant Analysis MUST NOT implicitly invoke that capability.
- **SRS-API-008:** DNA MUST expose target nomenclature as a separate optional capability boundary that applies the windows of an explicitly supplied target profile (`variant_nomenclature::apply`) and MUST NOT silently apply any target's nomenclature rules.
- **SRS-API-009:** DNA MUST expose a Rust library capability for Sanger sample analysis (`sample_analysis::analyze_sanger`) that accepts explicit trace, reference FASTA, and configuration paths and an explicit maximum number of worker threads, processes and places each trace once, and returns both the sample evidence and the consensus from that one placement pass. It MUST reuse the same read-processing, placement, rejection, aggregation, and consensus behavior as the `sample` and `consensus` commands. A companion call (`sample_analysis::analyze_sanger_outcome`) MUST run the same pass and return, when no read is admitted, every rejected read with its cause instead of the `NoAdmittedReads` error, and otherwise exactly the same analysis or error.
- **SRS-API-010:** The Sample Analysis result MUST be typed: reference and target-profile identities, the target profile's reportable regions, the core sample evidence (which carries the configuration identity), the consensus, the Sanger evidence of each admitted read, and each rejected read with its cause and, unless it was too short to process, its Sanger evidence, keyed by read content SHA-256. It MUST NOT expose the versioned JSON report DTOs.
- **SRS-API-011:** Calling the Sample Analysis API, including `SampleAnalysis::call`, MUST NOT create operational log files, derive or validate CLI output paths, serialize JSON, or publish result files. Its result MUST NOT depend on the number of workers or on how its reads are scheduled, and a failure MUST be that of the first failing trace in input order, whether a typed error or a panic. Each read's instrumentation MUST go to the caller's current dispatcher inside the caller's current span.
- **SRS-API-012:** A Sample Analysis MUST be callable in process (`SampleAnalysis::call`) for a given sample identifier: the consensus MUST be called with the analysis's configuration, profile, and reference exactly as `call` calls the consensus document that `consensus` publishes, from the consensus's decided edits (SRS-VAR-021), completing the recommended `consensus` then `call` workflow. The typed result MUST hold the consensus segments' callable reference segments and the sample's notation calls exactly as `notation.calls[].call` of the `dna.variants/v1` document `call` would publish, each with its position, insertion ordinal, and reference and called bases.
- **SRS-API-013:** A Sample Analysis MUST expose, read-only (`SampleAnalysis::observations`), every admitted read's observation of each reference position of a requested inclusive 1-based interval that a read covers, whether or not a read differs from the reference there, as the same observation records and with the same read indices as the differential loci of the sample evidence, without their support aggregates. A zero or reversed interval MUST fail typed; the interval does not wrap the circular origin. It MUST NOT change the sample evidence or the consensus.
- **SRS-API-014:** `dna review <sample-id> <trace>... --reference <fasta>` MUST run the in-process path of SRS-API-012 once (the sample placement pass with its rejections, the consensus, and `SampleAnalysis::call`) and write one `results/<sample-id>.review.json` identified as `dna.review/v1`, failing without output only on an input, configuration, or publication error. Every sample MUST get a document whose `status` is `called`, `rejected` (every read rejected; the reads with their causes and no items), or `call_failed` (the failure text, and the items without calls). The document MUST carry the provenance with the labelling-rules version, every read with its strand or rejection, the sample's calls, callable ranges, and EMPOP query when the call succeeded, the review items in priority order with their labels and per-read evidence, and a summary whose `clear` holds only for a called sample without a `check` item. Items and labels MUST follow the rules of the [review reference](../reference/review.md), derive from DNA's own evidence only, and be byte-identical for the same inputs whatever the number of workers.
